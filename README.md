# Vexi Telegram Bot for LEADUP

Готовый Python-сервис, который напрямую читает **ту же Supabase-базу**, что и LEADUP CRM, и публикует достижения команды в Telegram.

## Что публикует

- 🚀 переход на **Грейд II** при 6 лидах за смену;
- 🔥 переход на **Грейд III** при 8 лидах;
- 🏆 переход на **Грейд IV** при 11 лидах;
- 🏆 личный рекорд оператора (публично только начиная с 6+ лидов, один раз за день);
- ✅ закрытие дневного плана;
- 🎯 100% личного месячного плана, включая отдельную подачу при досрочном выполнении;
- 🎯 100% месячного плана группы;
- 🚀 100% месячного плана всего отдела;
- 🔥 новый рекорд группы за день;
- 🚀 новый рекорд всего отдела за день.

- 🏷 **тег участника «Грейд I / II / III / IV»** в рабочем чате у каждого, кто привязал Telegram в LEADUP (см. «Привязка Telegram и теги»).

Грейд — **дневной, а не постоянный**: каждый новый день счетчик начинается заново. Оператор снова проходит ступени II → III → IV по результату текущей смены.

В сообщениях о грейде показывается действующая ставка этой ступени.

## Как бот «читает сайт»

Он не парсит HTML и не открывает LEADUP как браузер.

```text
LEADUP (Next.js)
      │
      ├── создаёт / меняет лиды
      ▼
   Supabase  ◄──────── Python Vexi Bot
      │                      │
      │                      └──► Telegram-чат
      └── единый источник данных
```

LEADUP и бот смотрят на одни таблицы `leads`, `operators`, `groups`, `plans`, `kv`. Поэтому закрытый браузер никак не мешает боту работать.

Для Telegram-достижений учитываются **только лиды со статусом `done` («Доведён»)**. Лиды `work` («В работе») и `failed` («Не доведён») не двигают грейды, рекорды и выполнение планов. Планы разрешаются в том же порядке: план конкретного месяца → карточка сотрудника/группы → общие настройки.

## 1. Создать Telegram-бота

1. Открыть `@BotFather`.
2. `/newbot`.
3. Сохранить токен.
4. Добавить бота в рабочий чат. Админ-права для обычной отправки сообщений не обязательны, но у бота должно быть право писать в чат.

## 2. Подготовить Supabase

Открой Supabase → **SQL Editor** и один раз выполни:

`sql/001_vexi_bot.sql`

Затем — миграцию привязки Telegram (из корня репозитория LEADUP):

`supabase/migrations/20260923000001_telegram_link.sql`

Обе безопасно запускать повторно; существующие `telegram_bot_events` / `telegram_bot_state` и история событий не трогаются. Пока вторая миграция не выполнена, бот работает как раньше — просто без тегов и `/link` (и сам включит их в течение минуты после выполнения, без рестарта).

Скрипт добавляет только 2 технические таблицы:

- `telegram_bot_events` — защита от повторных поздравлений;
- `telegram_bot_state` — ID подключенного Telegram-чата и состояние сервиса.

Существующие таблицы LEADUP не меняются.

## 3. Service Role key

В Supabase возьми серверный **Service Role key**. Он нужен, потому что бот должен видеть результаты всей команды независимо от RLS конкретного пользователя.

**Никогда не вставляй Service Role key в `NEXT_PUBLIC_*`, frontend или GitHub.** Он должен быть только в Variables отдельного Railway-сервиса бота.

## 4. Переменные Railway

Создай отдельный Service в том же Railway Project и добавь:

```env
TELEGRAM_BOT_TOKEN=...
SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_SERVICE_ROLE_KEY=...
BOT_SETUP_SECRET=случайная-длинная-строка
POLL_INTERVAL_SECONDS=4
REFERENCE_REFRESH_SECONDS=30
LOG_LEVEL=INFO
APP_TIMEZONE=Europe/Moscow
```

Необязательно: `TELEGRAM_BOT_USERNAME` (иначе берётся из `getMe()`), `TAG_RECONCILE_SECONDS=300`, `TAG_VERIFY_SECONDS=3600`.

При желании укажи свой Telegram user id:

```env
TELEGRAM_ADMIN_IDS=123456789
```

Тогда `/connect`, `/status`, `/test` сможет выполнять только этот пользователь.

## 5. Railway

### Вариант A — отдельный репозиторий

Залей эту папку в GitHub и подключи репозиторий к Railway. `Dockerfile` и `railway.json` уже готовы.

### Вариант B — положить в текущий LEADUP repo

Положи папку, например, в `/telegram-bot`. В новом Railway Service укажи **Root Directory = `/telegram-bot`**.

Это правильнее, чем запускать Next.js и Telegram long polling одним процессом.

## 6. Подключить рабочий чат

После запуска добавь бота в Telegram-группу и напиши там:

```text
/connect значение_из_BOT_SETUP_SECRET
```

Бот ответит:

```text
✅ ЧАТ ПОДКЛЮЧЕН

Vexi теперь связан с LEADUP.
Новые достижения будут появляться здесь автоматически.
```

После этого можно выполнить `/test`.

## Как выглядит грейд

```text
🚀 НОВЫЙ ГРЕЙД

6 лидов. Иван Петров переходит на Грейд II.

┃ 💰 230 ₽/ч + 75 ₽ за лид
┃ До следующей ступени: 2 лида
```

В самом Telegram последняя часть рендерится штатной цитатой (`blockquote`), а ключевые цифры выделены жирным.

## Важная защита от спама

- каждый грейд публикуется только один раз на оператора **в конкретный день**; на следующий день путь по грейдам начинается заново;
- личный рекорд — максимум одно сообщение на оператора в день;
- дневной план — одно сообщение в день;
- месячный план — одно сообщение на месяц;
- рекорд группы/отдела — одно сообщение в день;
- при первом подключении бот **не вываливает старые достижения**: текущие события помечаются как уже существующие;
- после обычного перезапуска Railway журнал в Supabase остается, поэтому старые поздравления повторно не отправляются.

## Команды

- `/start` — описание; `/start link_482913` — привязка по ссылке из LEADUP;
- `/link 482913` — привязать свой Telegram к карточке оператора (только в личке с ботом);
- `/connect SECRET` — привязать текущую группу как рабочий чат;
- `/status` — чат, Supabase, права на теги, сколько операторов привязано;
- `/test` — тестовая красивая карточка грейда.

## Привязка Telegram и теги

**Оператор:** LEADUP → «Мой день» → блок **Telegram** → «Подключить Telegram» → «Открыть Vexi». Ссылка `t.me/<bot>?start=link_XXXXXX` привязывает аккаунт сама; вручную — `/link XXXXXX`.

Код — 6 цифр, живёт 15 минут, одноразовый, новый код гасит прежний; в базе хранится только хэш с солью. После 8 неверных попыток за 15 минут Telegram-аккаунт получает паузу. Один Telegram — одна карточка. Идентификатор — только `telegram_user_id`; username и имя — для показа.

**Тег** в рабочем чате = грейд за сегодня (APP_TIMEZONE) по **доведённым** лидам (`done`):

| Доведено сегодня | Тег |
|---|---|
| 0–5 | Грейд I |
| 6–7 | Грейд II |
| 8–10 | Грейд III |
| 11+ | Грейд IV |

- тег меняется при любом изменении лида — и вверх, и вниз (done → failed возвращает прежнюю ступень);
- при переходе на II/III/IV тег меняется **до** поздравления; если Telegram временно не принял тег, поздравление всё равно уходит, а тег догонит сверка;
- новый день: в течение ~15 с после 00:00 по APP_TIMEZONE все получают «Грейд I» (без сообщений в чат);
- сверка при старте, раз в `TAG_RECONCILE_SECONDS` и полная перепроверка через `getChatMember` раз в `TAG_VERIFY_SECONDS` — рестарт, ночной простой и редеплой не оставляют вчерашних тегов;
- последний поставленный тег хранится в `operator_telegram.tag_synced` — лишних запросов к Telegram нет;
- человек не в чате / вышел / вступил позже — статус видно в LEADUP, тег ставится, как только он появится в чате;
- отключение в LEADUP снимает тег (очередь `telegram_unlinks`); ошибка снятия не мешает отвязке.

### Права бота в рабочем чате

Бот должен быть **администратором** с правом **«Управление тегами» (Manage tags / `can_manage_tags`)**. Остальные админ-права для тегов не нужны. Без него бот продолжает публиковать достижения, пишет в лог `telegram.tag.failed … reason=rights:no_manage_tags` и один раз (не чаще раза в сутки) предупреждает чат. Как только право выдали — теги расставляются сами.

Ограничения Telegram: тег — до 16 символов без эмодзи; **администраторам чата тег поставить нельзя** (у них своё «звание»); бот видит вход участников только будучи админом (иначе — периодическая сверка).

### Логи

`telegram.link.success operator_id=… telegram_user_id=…`, `telegram.link.rejected … reason=expired code=48****`, `telegram.tag.changed operator_id=… from=grade1 to=grade2`, `telegram.tag.failed operator_id=… reason=…`, `telegram.reconcile.completed reason=… total=… changed=… failed=…`, `telegram.day.rollover`. Токен, ключ Supabase и коды целиком не логируются (`httpx` приглушён: он печатал URL Bot API вместе с токеном).

## Принцип обработки

Сервис раз в несколько секунд проверяет `leads.updated_at`. Когда супервайзер переводит лид из `work` в `done`, бот видит изменение `updated_at`, добавляет этот лид в подтвержденный факт и только после этого проверяет грейды, рекорды и планы. `work` и `failed` в достижениях не считаются. Справочники операторов, групп, планов и настройки CRM регулярно обновляются из Supabase.

Это сделано специально без парсинга сайта: изменение интерфейса LEADUP не ломает Telegram-бота, пока структура данных остается той же.


## Версия подсчёта done-only

Начиная с этой версии все достижения считаются только по `done`. Внутри используется новый namespace событий `done_v2` и отдельная метка инициализации. Поэтому старые события, записанные версией, где считались `work + done`, не блокируют новые корректные уведомления. При первом запуске этой версии уже существующие достижения по `done` тихо фиксируются без спама в чат.
